# SynapseHub Database Schema and Tech Stack

## 1. Database Schema (PostgreSQL + Prisma)

### Database engine
- `PostgreSQL` is the primary system of record.
- Schema is defined in `packages/shared/prisma/schema.prisma`.
- All services use Prisma Client generated from this shared schema.

### Core enums
- `WorkspaceRole`: `OWNER`, `ADMIN`, `MEMBER`, `GUEST`
- `ChannelType`: `PUBLIC`, `PRIVATE`, `DIRECT`
- `MessageType`: `TEXT`, `SYSTEM`, `BOT`
- `NotificationType`: `MENTION`, `DIRECT_MESSAGE`, `THREAD_REPLY`, `CHANNEL_ACTIVITY`, `SYSTEM`
- `DeliveryStatus`: `PENDING`, `SENT`, `FAILED`
- `IntegrationType`: `GITHUB`, `WEBHOOK`, `CUSTOM` (`GITHUB` reserved in schema, not enabled by API)
- `AuditAction`: `CREATE`, `UPDATE`, `DELETE`, `INVITE`, `LOGIN`, `LOGOUT`, `ROLE_CHANGE`, `BOT_COMMAND`, `INTEGRATION_EVENT`
- `BotEventType`: `MESSAGE_CREATED`, `MESSAGE_REACTION`, `CHANNEL_JOINED`, `SLASH_COMMAND`

### Main tables and responsibilities
- `User`: account profile and identity fields.
- `OAuthAccount`: reserved table for future external auth providers (not enabled in current API).
- `RefreshToken`: hashed refresh token lifecycle.
- `EmailVerificationToken`: one-time email verification tokens.
- `PasswordResetToken`: one-time password reset tokens.
- `Workspace`: tenant boundary for collaboration data.
- `WorkspaceMember`: many-to-many user membership with role.
- `WorkspaceInviteLink`: expiring invite links with role/domain/email constraints.
- `WorkspaceInviteAcceptance`: invite acceptance audit and idempotency record.
- `Channel`: conversation space inside a workspace.
- `ChannelMember`: user membership inside channels.
- `Message`: ordered messages in channels and threads.
- `Thread`: thread root + channel/workspace references.
- `Reaction`: emoji reactions on messages.
- `File`: file metadata and storage pointers.
- `Notification`: user notification inbox and delivery state.
- `Bot`: bot identity and scopes for workspace automation.
- `BotEvent`: events handled/generated by bots.
- `Integration`: webhook/custom integration config.
- `AuditLog`: security and operational audit trail.

### Key relationships (connection map)
- `User 1->N Workspace` (owner via `Workspace.ownerId`)
- `User 1->N EmailVerificationToken`
- `User 1->N PasswordResetToken`
- `User N<->N Workspace` via `WorkspaceMember`
- `Workspace 1->N WorkspaceInviteLink`
- `WorkspaceInviteLink 1->N WorkspaceInviteAcceptance`
- `Workspace 1->N Channel`
- `User N<->N Channel` via `ChannelMember`
- `Workspace 1->N Message`
- `Channel 1->N Message`
- `User 1->N Message` (author)
- `Thread 1->N Message` (thread replies)
- `Message 1->N Message` (parent/replies self relation)
- `Message 1->N Reaction`
- `User 1->N Reaction`
- `Workspace 1->N File`
- `User 1->N File` (uploader)
- `Message 0..1<->N File` (optional attachment link)
- `User 1->N Notification`
- `Workspace 1->N Bot`
- `Bot 1->N BotEvent`
- `Workspace 1->N Integration`
- `Workspace 1->N AuditLog`

### Integrity and performance design
- Unique constraints for membership pairs:
  - `WorkspaceMember(workspaceId, userId)`
  - `ChannelMember(channelId, userId)`
- Message ordering guarantee:
  - `Message(channelId, sequence)` unique index
- Frequent access indexes:
  - timeline queries: `Message(channelId, createdAt)`
  - user inbox: `Notification(userId, isRead, createdAt)`
  - workspace filtering on channels/files/logs/messages

### Service-to-database connection pattern
- All domain services connect to the same PostgreSQL database using `DATABASE_URL`.
- Prisma migrations are applied by the `migrator` container before services start.
- Shared migration commands:
  - `npm run prisma:deploy --workspace @synapsehub/shared`
  - `npm run prisma:push --workspace @synapsehub/shared`

## 2. Tech Stack Used and Why

### Frontend
- `Next.js` + `React` + `TypeScript`
  - Why: production-grade routing/rendering, component model, static typing.
- `TailwindCSS`
  - Why: fast, consistent UI development.
- `React Query`
  - Why: cache management, async state, mutation handling.

### Backend
- `Node.js` + `NestJS` + `TypeScript`
  - Why: modular architecture, DI, and scalable service boundaries.
- `Prisma ORM`
  - Why: type-safe queries and schema-first migrations.

### Realtime and async
- `Socket.IO`
  - Why: reliable WebSocket abstraction with rooms and reconnect behavior.
- `Redis Pub/Sub`
  - Why: cross-instance realtime event fanout.

### Data and search
- `PostgreSQL`
  - Why: strong relational consistency for multi-entity collaboration data.
- `Elasticsearch` (search service integration path)
  - Why: scalable full-text search workloads.
- `S3-compatible object storage` (MinIO locally)
  - Why: decoupled binary file storage.

### Infrastructure and operations
- `Docker` + `Docker Compose`
  - Why: reproducible local and CI runtime.
- `Kubernetes`
  - Why: orchestration and horizontal scaling in production.
- `Terraform`
  - Why: infra as code and environment repeatability.
- `GitHub Actions`
  - Why: automated build, test, and deployment workflows.
- `Prometheus` + `Grafana` + `ELK`
  - Why: metrics, dashboards, and centralized logs.

## 3. Current Architecture Note
- SynapseHub is implemented as microservices with an API gateway.
- Services are logically separated by domain but currently share one PostgreSQL schema.
- This gives faster development and strong relational consistency while preserving a path to future database separation if needed.

## 4. Excluded Third-Party Platforms
- Microsoft Purview eDiscovery
- GitHub webhooks, Jira, ServiceNow, PagerDuty product connectors
- Google OAuth, GitHub OAuth, enterprise SSO/SCIM provisioning
- Stripe subscriptions, Stripe webhooks, Stripe customer portal
